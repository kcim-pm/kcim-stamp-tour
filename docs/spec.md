# 스탬프 투어 개발 명세서

개발자가 코드를 쓸 때 맞추는 기준 문서다. 화면이 어떻게 구성되는지, 데이터가 어떻게 생겼는지, API가 무엇을 주고받는지를 적는다. 배경, 일정, 비용, 미확정 결정은 [기획서](plan.md)에 있다. 기획서의 결정이 바뀌면 이 문서의 해당 장에 반영한다.

| ----- | ------------------------ |

| 기획서   | `docs/plan.md`           |
| 최종 수정 | 2026-10-16               |

## 1. 요약

- 참가자는 구역의 QR을 스캔해 참가번호를 입력하고 방문을 인증한다. 구역 5곳을 모두 돌면 자동으로 추첨에 응모된다.
- 운영자는 관리자 콘솔(노트북 화면)에서 현황을 관리하고, 별도 창의 발표 화면(프로젝터)에서 미리 등록한 경품 순서대로 추첨한다. 현장에 없는 당첨자는 재추첨한 뒤 확정한다.
- Next.js 앱을 Netlify에 올리고, 데이터는 Supabase PostgreSQL에 둔다. 브라우저는 DB에 직접 접근하지 않고 항상 Next.js API를 거친다.

## 2. 기능 요구사항

우선순위: **필수**(행사 운영에 꼭 필요) / **중요**(시간 안에 완성 목표) / **후순위**(단순하게 처리).

### 2.1 참가자 기능

| ID | 기능 | 우선순위 | 요구사항 |
|---|---|---|---|
| P-01 | 모바일 웹 참여 | 필수 | 앱 설치나 회원가입 없이 스마트폰 브라우저로 쓴다 |
| P-02 | 구역별 QR 진입 | 필수 | QR 주소의 토큰으로 구역을 알아내 「현재 위치」로 보여 준다 |
| P-03 | 참가번호 입력 | 필수 | 명찰에 적힌 1~999 번호를 입력한다. 새로 발급하지 않는다. `007`처럼 앞자리 0이 붙어도 `7`로 정규화한다 |
| P-04 | 참가번호 기억 | 필수 | 인증이나 조회에 성공한 번호를 브라우저에 저장하고, 다음부터 입력란에 미리 채운다 |
| P-05 | 방문 인증 | 필수 | 번호 입력란과 [방문 인증하기] 버튼이 한 카드에 있다. 버튼 한 번으로 인증이 끝난다. 방문 순서는 제한하지 않는다 |
| P-06 | 인증 현황 | 필수 | 「N / 5곳 완료」 숫자, 진행 바, 구역마다 「인증 완료 / 대기」 배지를 보여 준다. 완주 전에는 「5곳을 모두 방문하시면 경품 추첨에 자동으로 응모됩니다」, 완주 후에는 「추첨 응모 완료」 배지 |
| P-07 | 완주 처리 | 필수 | 서로 다른 구역 5곳을 모두 인증하면 완주다 |
| P-08 | 추첨 자동 응모 | 필수 | 완주하면 자동으로 응모되고, 완주 카드로 안내한다 |
| P-09 | 상태 복원 | 필수 | 다시 접속하거나 다른 기기에서 같은 번호를 입력하면 서버 기록으로 현황을 복원한다 |
| P-10 | 참가번호 제시 | 중요 | 완주 카드에 참가번호를 `#132`처럼 크게 표시한다. 선물을 받을 때 이 카드를 보여 준다. 별도 화면은 없다 |
| P-11 | 현황 조회 | 필수 | QR 없이 들어와도 번호를 입력해 현황을 볼 수 있다 |

참가자 화면에는 당첨 여부를 표시하지 않는다. 당첨 번호는 발표 화면(3.4)에만 나오고, 본인 확인은 현장에서 명찰의 번호와 대조한다.

### 2.2 운영자 기능

| ID | 기능 | 우선순위 | 요구사항 |
|---|---|---|---|
| A-01 | 관리자 인증 | 필수 | 공용 관리자 비밀번호를 입력해야 콘솔과 발표 화면에 들어갈 수 있다(D-12) |
| A-02 | 구역별 QR 제공 | 필수 | 구역 5곳마다 고화질 QR(SVG)을 만든다 |
| A-03 | QR 포스터 인쇄 | 필수 | 인쇄 버튼과 A4 레이아웃을 둔다. 포스터에 구역 이름, QR, 3줄 안내문(QR 스캔 → 명찰 번호 입력 → 방문 인증하기)을 넣는다 |
| A-04 | 통계 | 필수 | 전체 참가자, 완주자, 진행 중 인원을 보여 준다 |
| A-05 | 참가자 목록 | 필수 | 번호마다 구역별 인증, 완주, 당첨 경품을 보여 준다 |
| A-06 | 자동 갱신 | 중요 | 1분마다 갱신한다. 켜기·끄기 스위치를 두고, 탭이 보이지 않으면 멈추고, 켠 지 30분이 지나면 자동으로 꺼진다. 서버를 바로 호출하는 [새로고침] 버튼을 따로 둔다 |
| A-08 | 참가자 삭제 | 중요 | 번호를 지정해 참가자와 방문·당첨 기록을 지운다 |
| A-09 | 발표 화면 | 필수 | `/admin/draw`를 새 창으로 열어 프로젝터에 띄운다. 전체 화면이고, 당첨 번호는 이 화면으로만 발표한다. 화면에 버튼·입력란·안내문을 두지 않고 키보드로만 조작한다(D-20) |
| A-10 | 추첨 후보 | 필수 | 「완주자 − 확정된 이전 당첨자」로 후보를 만든다(D-04). 부재자로 재추첨된 사람은 빼지 않는다 |
| A-11 | 당첨 인원 | 필수 | 경품 목록에 등록한 인원을 기본값으로 쓴다. 추첨 직전에 바꾸려면 관리자 콘솔의 경품 목록에서 고치고 발표 화면을 새로고침한다(D-22) |
| A-12 | 경품 목록 | 필수 | 이름, 당첨 인원, 순서를 미리 등록한다. 등급은 따로 두지 않고 「5등 커피」처럼 이름에 적는다. 추첨은 이 순서대로 진행한다(D-19). 이미 추첨한 경품은 수정·삭제할 수 없다. 추첨을 한 번이라도 시작한 경품은 확정 전이어도 이미 추첨한 경품이다. 경품 사진은 쓰지 않는다(D-21 폐기, 10/22) |
| A-13 | 당첨자 선정 | 필수 | 서버에서 무작위로 뽑아 저장한다 |
| A-14 | 추첨 연출 | 중요 | 당첨 칸이 인원만큼 처음부터 각자 세 자리 릴로 돌고, 첫 칸부터 하나씩 백→십→일 순으로 멈춘다. 한 칸이 멈추면 번호를 발표할 간격을 두고 다음 칸이 멈춘다. 번호는 003 처럼 세 자리로 채운다. 재추첨 때는 바뀐 번호의 칸만 다시 돈다. 효과음을 넣는다. 연출은 서버가 정한 결과를 보여 줄 뿐이다(D-23) |
| A-15 | 결과 표시 | 필수 | 당첨 번호를 상자 없이 숫자만 크게 보여 준다. 크기와 배치는 인원에 따라 정한다(3.4 「당첨 번호 배치」) |
| A-17 | 다음 경품 | 필수 | → 키로 목록의 다음 경품을 진행한다. 현재 회차를 확정하기 전에는 먹지 않는다 |
| A-18 | 결과 유지 | 필수 | 임시 결과와 확정 결과 모두 서버에 저장되어 창을 닫거나 새로고침해도 남는다(D-10) |
| A-23 | CSV 내보내기 | 필수 | 전체 참가자 현황을 UTF-8 BOM 포함 CSV로 내려받는다. 열: 참가번호, 구역별 인증 시각, 완주 여부, 당첨 경품 |
| A-24 | 부재자 재추첨 | 필수 | 임시 결과에서 번호를 눌러 고른 뒤 Space 키를 누르면 그 자리만 다시 뽑는다(D-18, D-22) |
| A-25 | 당첨 확정 | 필수 | Enter 키를 눌러야 회차가 확정된다. 확정 전에는 다음 경품으로 넘어갈 수 없다 |
| A-26 | 당첨 현황 패널 | 중요 | 발표 화면 옆에 경품을 추첨 순서의 역순(1등이 맨 위)으로 늘어놓는다. 등수는 추첨 순서를 거꾸로 센 값이다. 아직 차례가 오지 않은 경품은 등수와 인원만, 지금 뽑는 경품은 경품 소개 단계부터 이름을 함께, 확정되면 당첨 번호를 붙이고 진하게 표시한다. 지금 뽑는 경품은 띠로 표시한다. 상태 글자·전체 진행률은 보여 주지 않는다 |

명단 복사(옛 A-16)는 2026-10-15에 뺐다. 선물 지급 기록(옛 A-07 미지급자 필터, A-19~A-22 지급 버튼·지급 상태 수정·지급 진행률·지급 기록)도 같은 날 뺐다. 선물은 현장에서 명찰 번호와 대조해 주고 시스템에는 기록하지 않는다(D-06).

### 3.2 참가자 화면

참고 사이트와 같은 카드 구성이다. 위에서부터 순서가 고정되어 있고, 조건에 따라 카드가 나타나거나 내용이 바뀐다.

| 순서  | 카드       | 내용                                                                                                                                                                                                            |
| --- | -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | 머리글      | 「BIMlize Con 2026 스탬프 투어」. 제목 전체가 메인(`/`)으로 가는 링크이고 모양은 일반 제목과 같다. 오른쪽에 정보 아이콘(ⓘ)을 앞에 붙인 [이용 안내] 링크(`/manual`) |
| 2   | 현재 위치    | 가운데 정렬 카드. 토큰이 유효하면 핀 아이콘이 든 「현재 위치」 배지, 구역 이름(크게), 「번호를 입력하고 인증을 누르세요」. 토큰이 없으면 「나의 투어 현황」 배지, 「번호를 입력하면 지금까지의 인증 현황을 볼 수 있습니다」. 토큰이 틀리면 「잘못된 QR입니다」, 「구역에 붙은 QR을 다시 스캔해 주세요」 |
| 3   | 번호 입력·실행 | 라벨 「참가번호 입력」, 큰 숫자 입력란(숫자 키패드, 최대 3자리, 저장된 번호가 있으면 미리 채움), 보조문 「입장 명찰이나 등록 번호를 입력해 주세요.」. 버튼은 토큰이 유효하면 [방문 인증하기 →], 없으면 [현황 확인하기 →]. 토큰이 틀리면 [현황 확인하기 →]. 토큰이 유효하고 현재 번호의 현황에서 이 구역이 인증 완료면(새 인증·이미 인증 모두, 다시 열었을 때도 저장된 번호로 판단) 입력란을 비활성화하고 버튼을 뒤로 가기 아이콘이 붙은 [메인으로 돌아가기](`/`)로 바꾼다 |
| 4   | 결과 배너    | 인증 성공 「{구역} 인증 완료!」(초록). 이미 인증한 구역 「이미 인증한 구역입니다」(회색). 번호 오류 「1부터 999 사이의 번호를 입력하세요」(빨강). 잘못된 토큰 「잘못된 QR입니다. 구역에 붙은 QR을 다시 스캔해 주세요」(빨강). 통신 실패 「연결에 실패했습니다」와 [다시 시도](빨강) |
| 5   | 완주       | 완주자에게만 보인다. 다른 카드와 같은 흰 평면 카드(경계선). 트로피 Lottie 애니메이션(`public/lottie/winner.lottie`, 한 번 재생 후 마지막 프레임에서 멈춤), 「완주 성공!」, 「내 참가번호」와 `132` 크게(앞에 `#` 없음), 「5곳 인증 완료. 추첨에 무사히 응모되셨습니다!」, 「추첨 및 당첨자 발표는 행사 종료 후 진행될 예정입니다.」 |
| 6   | 인증 현황    | 번호가 있을 때 보인다. 「인증 현황 #132」, 「N / 5」. 완주 후에는 「✓ 추첨 응모 완료」 배지. 구역 5개를 S자 경로 위에 입체 스탬프(동전)로 놓고, 인증한 구역은 색을 채우고 대기 구역은 흐리게 둔다. 경로는 앞에서부터 연속으로 인증한 구간까지 진하게 칠한다. 구역이 5곳이 아니면 한 줄 배치로 대체한다. 경로와 스탬프는 318×214 비율을 지키며 카드 폭에 맞춰 함께 줄어들고, 스탬프 글자는 가운데 정렬·어절 단위 줄바꿈이다(10/22, 좁은 화면 넘침 수정). 경로 아래에 완주 전에는 「5곳을 모두 방문 후 인증하면 추첨에 자동 응모됩니다」, 완주 후에는 「✓ 추첨 응모 완료」 배지(가운데 정렬) |

**동작 규칙**

- [방문 인증하기 →]를 누르면 `POST /api/visit`를 부르고, 성공하면 번호를 브라우저에 저장하고 4~6번 카드를 갱신한다. 완주가 되면 5번 카드가 나타난다.
- [현황 확인하기 →]를 누르면 `GET /api/status`를 부르고, 성공하면 번호를 저장하고 5~6번 카드를 갱신한다.
- 저장된 번호가 있으면 화면을 열 때 자동으로 현황을 불러와 5~6번 카드를 먼저 채운다. 입력란에도 그 번호가 들어 있어, 토큰이 유효하면 바로 [방문 인증하기 →]만 누르면 된다.
- 번호를 바꾸는 별도 버튼은 없다. 입력란의 번호를 고쳐 [현황 확인하기 →]나 [방문 인증하기 →]를 누르면 그 번호로 조회·인증되고 저장 번호도 그 번호로 바뀐다(D-07).
- 번호는 어디서나 `7`처럼 앞자리 0 없이 표시한다. 인증 현황 제목에는 `#7`, 완주 카드의 큰 번호에는 `7`로 쓴다. 발표 화면 무대의 릴만 예외로 `007`처럼 세 자리로 채운다(3.4, D-23).
- 디자인 기준은 디자인 캔버스 「E 최종」(완주 전·후). 색·형태·동작은 `app/globals.css`에 두고 화면은 클래스만 붙인다. 반복 동작(경로 점선, 대기 스탬프 둥실, 색종이)은 `prefers-reduced-motion`이면 전부 끈다. Lottie 애니메이션은 재생하지 않고 마지막 프레임만 보여 준다. Lottie 플레이어는 그 장면이 뜰 때만 내려받는다(`next/dynamic`, `ssr: false`).

### 3.3 관리자 콘솔 (`/admin`)

| 영역 | 구성 |
|---|---|
| 로그인 | 세션 쿠키가 없으면 `/admin/login?next=/admin`으로 보낸다(3.6). 로그인 전에는 콘솔을 보여 주지 않는다 |
| 상단 버튼 | [발표 화면 열기] (`/admin/draw`를 새 창으로), [경품 목록], [QR 인쇄 페이지], [CSV 내려받기], [운영자 가이드] (`/admin/manual`), [로그아웃] |
| 통계 | 전체 참가자, 완주자, 진행 중 인원 |
| 참가자 목록 | 번호, 구역별 인증 여부, 완주, 당첨 경품, 삭제 버튼 |
| 경품 목록 | 이름, 당첨 인원을 등록·수정한다. 등급 칸은 없다(A-12). 추첨 순서는 표의 줄 순서이고 [↑][↓]로 바꾼다. 순서 숫자는 입력하지 않으며, 저장할 때 위에서부터 `sort`를 매긴다. 이미 추첨한 경품은 수정·삭제·이동할 수 없고 표 맨 위에 고정된다(A-12) |
| 운영자 가이드 (`/admin/manual`) | 콘솔과 같은 로그인 보호. 콘솔 머리글(「운영자 가이드」, [관리자 콘솔로])과 그 아래 읽기 폭(760px)의 본문. 행사 전 준비(로그인, 경품 등록, QR 인쇄) → 행사 중(참여 현황) → 경품 추첨(발표 화면, 추첨, 재추첨, 확정, 종료) → 행사 후(선물 지급, CSV, 로그아웃) 11단계와 운영자 자주 묻는 질문 6개. 카드 모양은 3.7과 같다(`components/manual-guide.tsx`). 참가자에게 관리자 화면 진입 방법과 캡처를 보이지 않으려고 3.7에서 분리했다 |
| 추첨 설정 | 「이전 당첨자 제외」 스위치 하나(처음엔 켜짐). 관객이 보는 발표 화면에 설정이 비치지 않도록 여기서 고친다(D-22). 당첨 인원은 경품 목록의 인원을 쓰고, 추첨 후보 수는 보여 주지 않는다 |
| 자동 갱신 | 1분 간격 스위치와 [새로고침] 버튼. 콘솔을 열면 스위치가 켜진 상태로 시작한다. 탭이 보이지 않으면 멈추고, 켠 지 30분이 지나면 자동으로 꺼진다. 마지막 갱신 시각을 표시한다 |

발표 화면에서 확정한 당첨 경품은 콘솔의 다음 갱신 때 반영된다. 바로 보려면 [새로고침]을 누른다.

추첨 설정은 DB 에 저장하지 않고 브라우저 저장소(localStorage)에 둔다. 콘솔과 발표 화면은 같은 브라우저의 같은 주소에서 열리므로, 콘솔에서 고치면 발표 화면이 새로고침 없이 바로 받는다. 다른 브라우저나 다른 PC 의 발표 화면에는 전해지지 않는다. 형식 검사는 `lib/draw-settings.ts` 가 한다.

### 3.4 추첨·발표 화면 (`/admin/draw`)

전체 화면 페이지다. 노트북에서 새 창으로 열어 프로젝터에 띄우고, 콘솔은 노트북 화면에 남긴다. 관리자 세션 쿠키가 없으면 `/admin/login`으로 보낸다(3.6). 경품 목록에 등록된 순서대로 한 경품씩 진행하고, 결과는 서버에서 먼저 정해지며 화면은 그 결과를 보여 줄 뿐이다. 가로 16:9 대형 화면 기준으로 설계한다. 관객이 보는 화면이므로 버튼·입력란·안내문을 두지 않고, 운영자는 무대 옆 노트북 키보드로만 조작한다(D-20). 디자인은 디자인 캔버스 「추첨 화면 개선안 비교」 두 번째·세 번째 줄을 따른다.

| 영역 | 구성 |
|---|---|
| 머리글 | 한 줄. 왼쪽에 행사 이름 「KCIM BIMlize Con 2026 · LUCKY DRAW」 |
| 무대 패널 | 머리글 아래 왼쪽(3/4 폭). 단계에 따라 경품 소개, 숫자 릴, 당첨 번호, 종료 화면이 들어간다. 경품 타이틀(이름·「N명 추첨」)은 패널 위쪽 왼쪽에 고정한다(10/22, 좌측 정렬) |
| 우측 패널 | 머리글 아래 오른쪽(1/4 폭), 무대 패널과 같은 높이. 「당첨 현황」: 경품을 추첨 순서의 역순으로 늘어놓아 1등이 맨 위에 온다. 등수는 경품 이름에서 읽지 않고, 콘솔 표의 줄 순서(`sort`)를 거꾸로 센다(경품 5개면 첫 번째 경품이 5등, 두 번째가 4등). 아직 차례가 오지 않은 경품은 「1등 (1명)」처럼 등수와 경품의 당첨 인원만 적고 흐리게 둔다. 지금 뽑는 경품은 경품 소개 단계부터 「3등 소형 안마기 (20명)」처럼 이름을 적고 연하늘색 띠로 표시한다(10/22). 확정되면 진하게 바꾸고 확정된 당첨 인원과 당첨 번호 칩을 붙인다. 임시 결과 단계에는 번호를 올리지 않는다. 상태 글자는 적지 않는다 |
| 운영자 패널 | 단축키 안내. Tab 키로 화면 아래에서 올라오고 다시 Tab 이나 Esc 로 닫는다. 단축키 표만 있다. 「이전 당첨자 제외」는 관리자 콘솔에 있다(3.3, D-22). 지금 단계에 맞지 않는 키는 흐리게 보이고, Space 는 추첨 시작과 재추첨 중 하나라도 되면 진하게 보인다. 관객에게도 보이므로 필요한 순간에만 연다 |

**조작 (키보드)**

| 키 | 동작 | 되는 단계 |
|---|---|---|
| Space | 준비 단계: 추첨 시작 / 결과(임시) 단계: 고른 번호 재추첨 | 준비, 결과(임시)에서 번호를 하나 이상 골랐을 때 |
| Enter | 당첨 확정 | 결과(임시) |
| → | 다음 경품 | 확정 후 |
| Tab | 운영자 패널(단축키 안내) 열기 · 닫기 | 언제나 |
| Esc | 패널 닫기, 고른 번호 해제 | 언제나 |

단계에 맞지 않는 키는 무시한다. 결과(임시) 단계에서 번호를 고르지 않고 Space 를 누르면 아무 일도 없다. 서버 요청 중에는 Tab 과 Esc 만 먹는다(두 번 눌러 회차가 두 개 생기는 것을 막는다). 일시정지(P)와 이전 결과(H)는 없다(D-22). 규칙은 `lib/draw-keys.ts` 에 두고 단위 테스트한다. 결과(임시) 단계에서 번호를 마우스로 눌러 부재자로 고르는 것은 그대로 둔다. 효과음은 첫 키 입력에서 잠금을 푼다.

**단계**

| 단계 | 화면 |
|---|---|
| 준비(경품 소개) | 무대 가운데에 경품 이름을 크게, 그 아래 「N명 추첨」(N 은 경품 목록의 당첨 인원). 경품 사진은 없다(10/22). 후보 수·스위치·입력란은 발표 화면에 없다 |
| 추첨 중 | 경품 타이틀 아래에 당첨 칸이 인원만큼 놓이고(배치는 「당첨 번호 배치」), 칸마다 세 자리 릴이 돈다. 자릿수마다 숫자가 아래에서 위로 빠르게 지나가고 자릿수끼리 박자가 어긋난다. 1.5초 뒤 첫 칸부터 하나씩 멈추는데, 칸 안에서는 백의 자리 → 십의 자리 → 일의 자리가 0.5초 간격으로 감속해 멈춘다(자릿수 하나 0.6초). 한 칸이 다 멈추면 MC 가 번호를 발표하도록 1초를 두고 다음 칸이 멈추기 시작한다. 번호는 `003`처럼 세 자리로 채운다. 멈춘 칸에 띠·상자·색을 두지 않는다. 시간 값은 `lib/winner-layout.ts`의 상수다(D-23) |
| 결과(임시) | 모든 칸이 멈춘 상태. 재추첨으로 빠진 부재자는 보이지 않는다. 번호를 눌러 부재자로 고르면 그 번호 뒤에 주황 면이 깔린다. Space 로 재추첨하면 바뀐 번호의 칸만 다시 돌다가 같은 방식으로 멈추고 잠깐 강조된다. 안내문과 버튼은 없다 |
| 확정 후 | 같은 번호를 같은 자리에 그대로 둔다. 「확정」 표시는 붙이지 않고, 우측 당첨 현황에 번호 칩이 쌓이는 것으로 확정을 안다 |
| 종료 | 마지막 경품을 확정하면 번호 없이 바로 이 화면이 된다. 가운데에 선물 Lottie 애니메이션(`public/lottie/gift.lottie`, 계속 반복), 「LUCKY DRAW」, 「모든 추첨이 끝났습니다」, 「참여해 주셔서 감사합니다」를 크게 보여 준다. 색종이가 떠오르고, 색종이는 참가자 화면 완주 카드와 같다. 마지막 당첨 번호는 우측 「당첨 현황」에서 본다 |

**당첨 번호 배치** (`lib/winner-layout.ts`, 단위 테스트)

번호는 상자·띠·체크 없이 숫자만 놓는다. 크기는 1280×720 기준 px 이고 화면 폭에 비례해 커진다.

| 인원 | 배치 | 크기 |
|---|---|---|
| 1명 | 하나를 가운데에 | 200px |
| 2명 | 둘을 가로로 | 160px |
| 3~5명 | 한 줄 격자(인원만큼 열) | 120px |
| 6~10명 | 5열 격자 | 96px |
| 11~20명 | 5열 격자 | 72px |
| 21명 이상 | 10열 격자 | 56px |

**동작 규칙**

- 확정 전에 창을 닫거나 새로고침해도 임시 결과는 서버에 남는다. 다시 열면 결과(임시) 단계부터 이어진다. 연출 중인지는 화면에만 있으므로 추첨 중에 새로고침하면 릴 없이 결과(임시) 단계가 나온다.
- 당첨 번호는 참가번호 오름차순으로 놓는다. 다만 재추첨으로 뽑힌 번호는 기존 번호 뒤에 재추첨한 순서대로 붙이고, 한 번에 여러 개를 뽑았으면 그 묶음 안에서만 오름차순으로 놓는다(`lib/winner-layout.ts`의 `winnerDisplayOrder`). 확정 후도 같은 순서다. 재추첨 번호는 끝자리여도 앞 칸을 기다리지 않고 바로 돌기 시작한다(한 번에 여러 개면 그 묶음 안에서만 첫 칸부터 차례로 멈춘다). 뽑힌 순서는 DB 에 저장하지 않고 발표 화면만 기억하므로, 새로고침하거나 창을 다시 열면 전체가 오름차순으로 돌아간다. 우측 당첨 현황은 언제나 오름차순이다.
- 재추첨은 고른 번호만 바꾼다. 나머지 번호는 그대로다. 재추첨된 번호(부재자)는 같은 회차에서 다시 뽑히지 않지만 다음 경품에서는 다시 후보가 된다.
- 확정 전에는 → 가 먹지 않는다.
- 마지막 경품을 확정하면 「종료」 단계가 되고 → 는 막힌다. 새로고침해도 종료 화면이 나온다.
- 번호는 대형 화면에서 읽히도록 크게 표시한다. 이 화면이 유일한 당첨 발표 수단이다.

### 3.5 QR 인쇄 페이지 (`/qr`)

구역 5곳마다 A4 세로 한 장씩. 구역 이름, QR(SVG), 3줄 안내문(① 이 QR을 스캔하세요 ② 명찰의 번호를 입력하세요 ③ [방문 인증하기]를 누르세요)을 넣는다. [인쇄] 버튼은 브라우저 인쇄 대화상자를 연다. 관리자 로그인이 필요하다(3.6).

### 3.6 관리자 로그인 페이지 (`/admin/login`)

비밀번호 입력란 하나와 [로그인] 버튼만 있는 페이지다. 아이디 입력란은 없다(D-12 공용 비밀번호 1개).

| 규칙 | 내용 |
|---|---|
| 보호 대상 | `/admin`, `/admin/draw`, `/admin/manual`, `/qr`과 관리자 API 전부. 세션 쿠키가 없거나 만료·위조되었으면 페이지는 `/admin/login?next={현재 경로}`로 보내고, API는 401 `UNAUTHORIZED`다 |
| 로그인 뒤 이동 | `next`가 `/`로 시작하고 두 번째 글자가 `/`나 `\`가 아닐 때만 그 경로로 돌아간다. 아니면(외부 주소, 빈 값) `/admin`으로 보낸다. 브라우저는 `/\evil.com`을 `//evil.com`과 같은 외부 주소로 해석하므로 역슬래시도 막는다 |
| 이미 로그인 상태 | 비밀번호를 묻지 않고 바로 `next`로 보낸다 |
| 오류 문구 | 401이면 「비밀번호가 틀립니다」, 그 외 실패는 「연결에 실패했습니다. 다시 시도해 주세요」 |
| 창 두 개 | 콘솔에서 [발표 화면 열기]로 연 새 창은 같은 쿠키를 쓰므로 다시 로그인하지 않는다 |

### 3.7 이용 안내 (`/manual`)

참가자 화면 머리글의 [이용 안내]가 가리키는 정적 페이지다. 로그인 없이 누구나 본다. 참가자 화면과 같은 휴대폰 폭 틀을 쓴다. 운영자 가이드는 여기에 없고 로그인 뒤 `/admin/manual`(3.3)에서 본다.

| 영역 | 구성 |
|---|---|
| 머리글 | 참가자 화면처럼 스크롤해도 위에 붙어 있다. 왼쪽에 배경 없는 돌아가기 꺾쇠(<, `/` 링크, 접근성 이름 「스탬프 투어로 돌아가기」), 그 옆에 「BIMlize Con 2026 이용 안내」. 오른쪽에는 아무것도 두지 않는다 |
| 참여 방법 | 제목 「참여 방법」. QR 찍기 → 번호 입력 → 방문 인증 → 완주·자동 응모 → 마지막 세션 종료 후 럭키 드로우 추첨 5단계. 안내 문단과 「QR 없이 내 스탬프 확인하기」 팁은 두지 않는다 |
| 자주 묻는 질문 | 참가자 6개. 펼쳐 보는 방식 |
| 바닥 | [맨 위로 ↑] |

**작성 규칙**

- 화면 배치는 바뀔 수 있으므로 버튼 위치보다 「무엇을 하면 어떻게 되는지」 흐름 위주로, 일반 참가자가 이해할 수 있는 말로 쓴다.
- 단계마다 화면 이미지를 붙인다. 이미지는 `public/manual/`에 두고, 화면이 바뀌면 직접 다시 찍는다(참가자 화면은 휴대폰 폭 390px·2배 해상도, 관리자·발표 화면은 1440~1600px 폭). 경품 이름은 「N번 경품」처럼 가린다. 이미지를 누르면 원본 크기로 열린다.
- 이미지에 QR 코드와 `?z=` 토큰이 나오면 안 된다(D-08). QR 인쇄 페이지는 QR을 가리고 찍는다.
- 운영자 가이드(`/admin/manual`)는 로그인 뒤에만 보이지만, 이미지는 `public/manual/`에 있어 주소를 알면 누구나 볼 수 있다. 관리자 비밀번호 등 비밀값은 문구에도 이미지에도 적지 않는다.

## 4. 데이터 모델

```sql
create table participants (            -- 첫 인증 시 생성. 사전 명단은 없다 (D-02)
  participant_no  smallint primary key check (participant_no between 1 and 999),
  created_at      timestamptz not null default now()
);

create table zones (
  id        smallint primary key,
  code      text unique not null,      -- zone1 ~ zone5. 이름이 나오면 name만 바꾼다 (D-15)
  name      text not null,
  qr_token  text unique not null,      -- 추측할 수 없는 랜덤 문자열
  sort      smallint not null
);

create table visits (
  participant_no  smallint references participants on delete cascade,
  zone_id         smallint references zones,
  visited_at      timestamptz not null default now(),
  primary key (participant_no, zone_id)   -- 같은 구역을 두 번 인증할 수 없다
);

create table prizes (                  -- 경품 목록. D-13 확정 후 seed.sql 또는 관리자 콘솔로 입력
  id            serial primary key,
  name          text not null,
  winner_count  smallint not null check (winner_count > 0),
  sort          smallint not null,     -- 추첨 순서. 콘솔 표의 줄 순서로 매긴다(3.3)
  image_url     text                   -- (쓰지 않음) 경품 사진 주소였다. 10/19 에 운영 DB 에 alter table 로 추가했고, 10/22 에 경품 사진을 없애면서 코드는 읽고 쓰지 않는다. 열은 지우지 않고 둔다
);

create table draws (
  id                serial primary key,
  prize_id          int not null references prizes,
  winner_count      smallint not null check (winner_count > 0),   -- 추첨 시점의 인원 (경품 목록에서 복사)
  exclude_previous  boolean not null default true,
  status            text not null default 'pending'
                    check (status in ('pending', 'confirmed')),   -- pending: 임시 결과, confirmed: 확정
  created_at        timestamptz not null default now(),
  confirmed_at      timestamptz
);

create table draw_winners (
  draw_id         int references draws on delete cascade,
  participant_no  smallint references participants on delete cascade,
  status          text not null default 'pending'
                  check (status in ('pending', 'confirmed', 'absent')),  -- absent: 부재자로 재추첨됨
  primary key (draw_id, participant_no)   -- 한 회차에 같은 사람이 두 번 당첨될 수 없다
);

-- 모든 테이블에 RLS를 켜고 공개 정책을 만들지 않는다. 서버 전용 키로만 접근한다.
alter table participants enable row level security;
alter table zones        enable row level security;
alter table visits       enable row level security;
alter table prizes       enable row level security;
alter table draws        enable row level security;
alter table draw_winners enable row level security;
```

- 완주 여부와 응모 여부는 따로 저장하지 않는다. `visits`에서 참가번호별 방문 구역 수가 `zones`의 전체 수와 같으면 완주이자 응모다.
- 「당첨자」는 `draw_winners.status = 'confirmed'`인 행이다. `absent` 행은 기록을 위해 남기고 당첨자로 세지 않는다.
- 선물 지급 여부와 지급 시각은 저장하지 않는다. 경품 등급(`rank`)과 지급 시각(`gift_given_at`) 칸은 `0001_init.sql`에서 뺐다.
- 구역과 경품 초기 데이터는 `supabase/seed.sql`에 둔다. `qr_token`은 seed.sql에서 `gen_random_uuid()`로 만든다(32자 16진수).

## 5. API 명세

### 5.1 공통 규칙

- 요청과 응답은 JSON이다. CSV 내보내기만 예외다.
- 관리자 인증은 공용 비밀번호 1개다(D-12). `POST /api/admin/login`에 비밀번호를 보내면 서버가 서명된 세션 토큰을 HttpOnly 쿠키로 발급한다. 관리자 API는 이 쿠키를 검증하고, 없거나 만료되었거나 서명이 틀리면 401이다.
- 오류 응답 형식. 본문에는 오류 코드만 담는다. 안내 문구는 화면이 HTTP 상태와 코드를 보고 정한다(3.2, 3.6).

```json
{ "error": "INVALID_TOKEN" }
```

| HTTP 상태 | 오류 코드 | 뜻 |
|---|---|---|
| 400 | `INVALID_BODY` | 요청 본문이 JSON이 아니다 |
| 400 | `INVALID_PARTICIPANT_NO` | 참가번호가 비었거나 1~999 정수가 아니다 |
| 400 | `INVALID_WINNER_COUNT` | 당첨 인원이 양의 정수가 아니다 |
| 400 | `INVALID_WINNER_SELECTION` | 재추첨 대상 번호가 이 회차의 임시 당첨자가 아니다(이미 부재자, 다른 회차 번호, 중복) |
| 401 | `UNAUTHORIZED` | 관리자 세션 쿠키가 없거나 만료되었거나 위조되었다 |
| 401 | `WRONG_PASSWORD` | 관리자 비밀번호가 틀리다 |
| 404 | `INVALID_TOKEN` | 토큰에 맞는 구역이 없다 |
| 404 | `DRAW_NOT_FOUND` | 재추첨·확정 요청의 회차 번호에 맞는 회차가 없다 |
| 409 | `NOT_ENOUGH_CANDIDATES` | 후보가 0명이라 뽑을 수 없다. 후보가 당첨 인원보다 적기만 하면 거부하지 않고 후보 수만큼 뽑는다 |
| 409 | `DRAW_PENDING_EXISTS` | 확정하지 않은 회차가 있어 새 추첨을 시작할 수 없다 |
| 409 | `DRAW_NOT_PENDING` | 이미 확정된 회차를 재추첨하거나 다시 확정하려 한다 |
| 409 | `PRIZE_ALREADY_DRAWN` | 이미 추첨해 확정한 경품을 바꾸거나, 그 경품으로 다시 추첨하려 한다 |
| 500 | `DB_ERROR` | DB 읽기·쓰기에 실패했다. 자세한 내용은 서버 로그에만 남긴다 |

### 5.2 참가자 API (공개)

**`GET /api/status?no={참가번호}`** 스탬프 현황과 완주 여부를 돌려준다. 당첨 여부는 돌려주지 않는다(D-05). 번호가 처음이면 `participants`에 행을 만들지 않고 방문 0건으로 돌려준다.

```json
{
  "participantNo": 7,
  "zones": [
    { "code": "zone1", "name": "구역 1", "visited": true, "visitedAt": "2026-10-27T13:12:00Z" },
    { "code": "zone2", "name": "구역 2", "visited": false, "visitedAt": null }
  ],
  "visitedCount": 1,
  "zoneCount": 5,
  "completed": false
}
```

**`POST /api/visit`** 방문을 인증한다. 토큰으로 구역을 찾고, 참가자가 없으면 만들고, 방문 기록을 넣는다.

요청: `{ "participantNo": "007", "zoneToken": "k8s2..." }` (문자열이든 숫자든 받아서 서버가 정수로 정규화한다)

응답(200): `alreadyVisited`와 함께 위 `GET /api/status`와 같은 현황을 돌려준다. 이미 방문한 구역이면 `alreadyVisited: true`이고 기록은 늘어나지 않는다.

```json
{ "zone": { "code": "zone1", "name": "구역 1" }, "alreadyVisited": false, "status": { "...": "GET /api/status 응답과 같음" } }
```

### 5.3 관리자 API

**`POST /api/admin/login`** 비밀번호를 확인하고 세션 쿠키를 발급한다.

요청: `{ "password": "..." }`
응답(204): `Set-Cookie: admin_session=<서명된 토큰>; HttpOnly; Secure; SameSite=Lax; Max-Age=43200` (12시간). 틀리면 401 `WRONG_PASSWORD`다. `Secure`는 운영 빌드에서만 붙인다. 로컬 개발(http)에서는 생략해야 쿠키가 저장된다.

**`POST /api/admin/logout`** 세션 쿠키를 지운다. 응답은 204다.

**`GET /api/admin/participants`** 통계와 참가자 목록을 돌려준다.

`zones`는 구역 순서(`sort`)대로이고, 콘솔 표의 열 제목에 쓴다. `visits`의 키는 구역 `code`다. `wins`는 확정된 당첨만 경품 순서대로 담는다.

```json
{
  "stats": { "total": 120, "completed": 80, "inProgress": 40 },
  "zones": [ { "code": "zone1", "name": "구역 1" }, { "code": "zone2", "name": "구역 2" } ],
  "participants": [
    {
      "participantNo": 7,
      "visits": { "zone1": "2026-10-27T13:12:00Z", "zone2": null },
      "completed": true,
      "wins": [ { "drawId": 1, "prizeName": "5등 경품" } ]
    }
  ]
}
```

**`DELETE /api/admin/participants/{참가번호}`** 참가자와 방문 기록, 당첨 기록을 지운다. 응답은 204다.

**`GET /api/admin/prizes`** 경품 목록을 추첨 순서대로 돌려준다. `drawn`은 이미 추첨한 경품인지다. 그 경품의 회차가 하나라도 있으면(임시 회차 포함) `true`다(A-12).

```json
{ "prizes": [ { "id": 1, "name": "5등 경품", "winnerCount": 10, "sort": 1, "drawn": false } ] }
```

**`PUT /api/admin/prizes`** 경품 목록을 통째로 저장한다. 이미 추첨한 경품을 바꾸거나 지우려 하면 409 `PRIZE_ALREADY_DRAWN`이다.

요청: `{ "prizes": [ { "id": 1, "name": "5등 경품", "winnerCount": 10, "sort": 1 } ] }` (`id`가 없으면 새로 만든다. 예전 콘솔이 보내던 `imageUrl`은 무시한다)

**`GET /api/admin/draws`** 추첨 이력과 당첨자를 돌려준다. 확정하지 않은 임시 회차도 포함한다. 뽑힌 순서는 저장하지 않으므로 `winners`는 참가번호 오름차순이다. `candidateCount`는 「이전 당첨자 제외」를 켰을 때의 후보 수, `completedCount`는 완주자 수(끈 때의 후보 수)다. 지금은 화면에 보여 주지 않는다(D-22).

```json
{
  "draws": [
    {
      "id": 1,
      "prize": { "id": 1, "name": "5등 경품" },
      "winnerCount": 10, "excludePrevious": true, "status": "confirmed",
      "createdAt": "2026-10-27T17:00:00Z", "confirmedAt": "2026-10-27T17:05:00Z",
      "winners": [
        { "participantNo": 7, "status": "confirmed" },
        { "participantNo": 42, "status": "absent" }
      ]
    }
  ],
  "candidateCount": 70,
  "completedCount": 80
}
```

**`POST /api/admin/draws`** 추첨을 실행하고 임시 결과를 저장한다. 확정하지 않은 회차가 남아 있으면 409 `DRAW_PENDING_EXISTS`, 그 경품에 이미 확정된 회차가 있으면 409 `PRIZE_ALREADY_DRAWN`이다.

요청: `{ "prizeId": 1, "winnerCount": 10, "excludePrevious": true }` (`winnerCount`를 생략하면 경품 목록의 인원을 쓴다)
응답(201): 위 `draws` 배열의 원소 하나와 같은 형식이다. `status`는 `pending`이다. 후보가 `winnerCount`보다 적으면 후보 수만큼만 뽑히고 `winnerCount`에는 요청한 인원이 남는다. 후보가 0명이면 409 `NOT_ENOUGH_CANDIDATES`다.

**`POST /api/admin/draws/{id}/redraw`** 선택한 번호를 부재자로 바꾸고 그 수만큼 다시 뽑는다.

요청: `{ "participantNos": [42, 108] }`
응답(200): 갱신된 회차. 선택한 번호는 `absent`, 새로 뽑힌 번호는 `pending`이다.
회차가 없으면 404 `DRAW_NOT_FOUND`, `pending`이 아니면 409 `DRAW_NOT_PENDING`, 번호가 이 회차의 `pending` 당첨자가 아니면 400 `INVALID_WINNER_SELECTION`이다.

**`POST /api/admin/draws/{id}/confirm`** 회차를 확정한다. `pending` 당첨자를 모두 `confirmed`로 바꾸고 `confirmedAt`을 기록한다. 응답(200)은 갱신된 회차다. 회차가 없으면 404 `DRAW_NOT_FOUND`, 이미 확정된 회차면 409 `DRAW_NOT_PENDING`이다.

**`GET /api/admin/export`** 전체 참가자 현황을 CSV로 돌려준다. `Content-Type: text/csv; charset=utf-8`, 본문 앞에 BOM을 붙인다. 구역 열은 인증 시각이고 미방문이면 비운다. 완주 열은 완주자만 `Y`, 아니면 빈칸이다. 당첨 경품은 확정된 것만, 여러 개면 세미콜론으로 잇는다(D-17). 시각은 모두 한국 시간 `YYYY-MM-DD HH:mm:ss`다. 줄 끝은 CRLF다.

```
참가번호,구역 1,구역 2,구역 3,구역 4,구역 5,완주,당첨 경품
```

## 6. 구현 규칙

| 규칙 | 구현 |
|---|---|
| 참가자 식별 | 참가번호(정수)가 기본키다. 방문·당첨 기록은 모두 참가번호로 연결한다 |
| 참가번호 정규화 | 입력값의 앞뒤 공백을 지우고 정규식 `^\d{1,3}$`을 통과하면 정수로 바꾼다. 1~999가 아니면 400 `INVALID_PARTICIPANT_NO`. `0`, `000`, `1000`, `7a`는 모두 거부한다. 브라우저에도 정수를 저장한다 |
| 참가자 생성 | `POST /api/visit`에서만 만든다. `GET /api/status`는 조회만 하고 만들지 않는다 |
| 구역 식별 | QR 주소의 토큰으로 `zones`를 조회한다. 없으면 404 `INVALID_TOKEN` |
| 중복 인증 방지 | `visits` 기본키 (참가번호, 구역)에 `ON CONFLICT DO NOTHING`으로 넣는다. 영향받은 행이 0이면 `alreadyVisited: true` |
| 완주 판정 | 참가번호별 `visits` 건수가 `zones` 전체 건수와 같다 |
| 추첨 후보 | 완주자 전체에서, `excludePrevious`가 참이면 확정된(`confirmed`) 이전 당첨자를 뺀다. 부재자(`absent`)는 빼지 않는다 |
| 재추첨 후보 | 추첨 후보에서 이 회차의 모든 당첨 기록(`pending`, `absent`)을 추가로 뺀다. 재추첨 인원보다 적으면 후보 수만큼만 뽑고, 0명이면 409 `NOT_ENOUGH_CANDIDATES` |
| 회차 상태 | 새 추첨은 `pending`으로 만든다. `pending` 회차가 있으면 새 추첨을 막는다. 재추첨과 확정은 `pending`에서만 한다 |
| 경품 순서 | `prizes.sort` 순서대로 진행한다. [다음 경품 →]은 확정된 회차가 없는 다음 경품을 고른다. 확정된 회차가 있는 경품으로 다시 추첨하면 409 `PRIZE_ALREADY_DRAWN`. 잘못 확정한 회차는 Supabase 대시보드에서 지운다 |
| 추첨 유효성 | 당첨 인원은 양의 정수다. 후보가 그보다 적으면 거부하지 않고 후보 수만큼 뽑는다. 후보가 0명일 때만 409 `NOT_ENOUGH_CANDIDATES` |
| 무작위성 | 서버에서 `crypto.randomInt`로 후보를 섞어 앞에서부터 뽑는다. 연출은 정해진 결과를 보여 줄 뿐이다 |
| 회차 안 중복 당첨 방지 | `draw_winners` 기본키 (회차, 참가번호). 비복원 추출이므로 같은 회차에 같은 번호가 두 번 나오지 않는다 |
| 권한 통제 | 추첨, 삭제, CSV는 관리자 API에서만 실행한다. 브라우저에서 DB를 직접 호출하지 않는다 |
| 창 두 개 | 콘솔과 발표 화면은 같은 세션 쿠키를 쓴다. 추첨 조작은 발표 화면에서만 한다. 발표 화면의 확정 결과는 콘솔의 폴링으로 반영된다 |
| 상태 공유 | 관리자 콘솔은 1분 폴링과 [새로고침]으로 최신 상태를 가져온다. 발표 화면은 조작 결과를 응답으로 바로 반영한다 |
| 오류 안내 | 번호 오류, 잘못된 QR, 통신 실패를 구분해 안내하고 통신 실패에는 [다시 시도]를 둔다 |

### 7.2 보안 원칙

- 브라우저에는 Supabase 키를 전혀 두지 않는다. 참가자 기능과 관리자 기능 모두 DB 읽기·쓰기는 Next.js API를 거친다.
- Supabase 키는 서버 전용 키(service_role) 하나만 쓰고, 서버 코드에서만 읽는다. `NEXT_PUBLIC_` 접두사를 붙이지 않는다.
- 그래도 모든 테이블에 RLS를 켜고 공개 정책을 만들지 않는다. 키가 새어도 anon 키로는 어떤 테이블도 읽거나 쓸 수 없다.
- 관리자 인증은 공용 비밀번호 1개다(D-12). 비밀번호는 환경변수에만 두고, 운영 스태프가 외울 수 있되 짐작하기 어려운 12자 이상 문구로 정한다. 맞으면 `ADMIN_SESSION_SECRET`(32바이트 이상 무작위)으로 서명한 토큰을 HttpOnly·Secure 쿠키로 발급하고 12시간 뒤 만료한다.
- 관리자 API는 매 요청마다 쿠키의 서명과 만료를 검증한다. 비밀번호 비교는 길이가 같을 때만 통과하는 상수 시간 비교 함수를 쓴다.
- 비밀 정보는 `.env.local`(로컬)과 Netlify 환경변수(배포)에만 두고 git에 올리지 않는다.

### 7.3 환경과 테스트 데이터 정리 (D-16)

Supabase 프로젝트는 `bimlizecon2026` 하나만 쓴다. 로컬 개발, Netlify 미리보기 배포, 운영 배포가 모두 같은 DB를 본다. 환경을 나누지 않는 대신 테스트가 끝날 때마다 데이터를 지운다.

| 리허설(10/26) 뒤 | 아래 SQL을 Supabase SQL 편집기에서 실행해 참가자·방문·추첨 데이터를 전부 지운다. 구역과 경품 목록은 남는다 |
| 행사 당일 아침 | 관리자 콘솔에서 참가자 0명, 추첨 0회인지 확인한다 |

### 7.5 로컬 개발 절차

1. 저장소를 받고 `npm install`을 실행한다.
2. 아래 명령을 두 번 실행해 `ADMIN_PASSWORD`와 `ADMIN_SESSION_SECRET` 값을 만든다.

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"
```

3. `.env.local`에 7.4의 환경변수 4개를 채운다. Supabase 값은 대시보드의 Project Settings → API에서 복사한다.
4. 테이블을 만든다. Supabase 대시보드(웹사이트)에 로그인해 왼쪽 메뉴 「SQL Editor」를 열고, `supabase/migrations/0001_init.sql`(4장의 SQL)을 붙여 넣어 Run을 누른다. 한 번만 하면 된다.
5. 초기 데이터를 넣는다. 같은 SQL Editor에서 `supabase/seed.sql`(구역 5개와 임시 경품 목록)을 붙여 넣어 Run을 누른다. 구역의 `qr_token`은 SQL 안에서 `gen_random_uuid()`로 자동 생성되므로, 실행 결과나 Table Editor의 `zones`에서 값을 확인한다.
6. `npm test`로 단위 테스트가 통과하는지 확인한다.
7. `npm run dev`로 띄우고 `http://localhost:3000/?z={토큰}`으로 참가자 화면을 확인한다.
8. `http://localhost:3000/admin`에 들어가면 `/admin/login`으로 보내진다. `ADMIN_PASSWORD` 값으로 로그인해 `/admin`으로 돌아오는지 확인하고, [발표 화면 열기]로 `/admin/draw`가 새 창에 뜨는지 확인한다.

Supabase CLI는 쓰지 않는다. SQL 파일을 대시보드에 붙여 넣는 것으로 충분하다.

## 8. 검증

### 8.1 단위 테스트

코드는 AI가 작성하므로 TDD로 진행한다. 기능마다 테스트를 먼저 쓰고, 실패를 확인한 뒤, 통과하는 코드를 쓴다. 도구는 Vitest이고 `npm test`로 실행한다. DB나 네트워크 없이 돌 수 있도록 규칙은 `lib/` 아래 순수 함수로 두고, Route Handler는 그 함수를 부르기만 한다.

| 모듈                      | 테스트할 규칙               | 예                                                                     |
| ----------------------- | --------------------- | --------------------------------------------------------------------- |
| `lib/participant-no.ts` | 참가번호 정규화 (6장)         | `"007"` → 7, `" 42 "` → 42, `"0"` · `"1000"` · `"7a"` · `""` → 거부     |
| `lib/completion.ts`     | 완주 판정                 | 방문 구역 수가 전체 구역 수와 같을 때만 참                                             |
| `lib/status.ts`         | 현황 계산, 이 구역 인증 여부 (3.2) | 구역별 방문·방문 시각, 방문 수·완주. 이 구역이 방문 완료일 때만 참, 미방문·없는 구역·현황 없음은 거짓 |

- [ ] 발표 화면을 닫고 다시 열어도 결과가 남는다. 확정 전 임시 결과도 남는다.

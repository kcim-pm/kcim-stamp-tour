# 스탬프 투어 이벤트 기획서

무엇을 왜 만들고, 언제까지, 얼마로, 행사 당일 어떻게 운영하는지를 적은 문서다. 코드를 어떻게 쓸지는 [개발 명세서](spec.md)에 있다. 결정이 바뀌면 이 문서의 2장을 먼저 고치고, 개발 명세서의 해당 장에 반영한다.

| 항목     | 내용                         |
| ------ | -------------------------- |
| 문서 위치  | `docs/plan.md`             |
| 개발 명세서 | `docs/spec.md`             |
| 최종 수정  | 2026-10-16                 |

## 1. 무엇을 만드는가

| 항목     | 내용                                                        |
| ------ | --------------------------------------------------------- |
| 행사     | KCIM BIMlize Con 2026                                     |
| 목적     | 행사 참가자가 행사장 구역을 돌며 스탬프를 모으고, 완주자 중에서 경품 당첨자를 뽑는 모바일 웹 서비스 |
| 참가자 규모 | 최대 150명, 평균 120명                                          |
| 운영일    | 2026-10-27(화) 12:40 ~ 17:00                               |
| 구역     | 행사장 안 5곳. QR 5개 설치 예정 (이름은 2.4 참조)                        |
| 운영 주소  | `bimlizecon2026.netlify.app`                              |
| 저장소    | `kcim-stamp-tour`                                         |

**참가자가 하는 일**

1. 구역에 붙은 QR을 스캔한다.
2. 처음 한 번만 참가번호를 입력한다. 이후에는 브라우저가 기억한다.
3. [방문 인증하기]를 눌러 스탬프를 받는다.
4. 모든 구역을 돌면 자동으로 추첨에 응모된다.
5. 발표 화면에 자기 번호가 나오면 명찰을 보여 주고 선물을 받는다.

**운영자가 하는 일**

1. QR 포스터를 인쇄해 구역마다 붙인다.
2. 관리자 콘솔에서 참여 현황을 본다.
3. 미리 등록한 경품 목록 순서대로 추첨한다. 발표 화면에 당첨 번호를 띄우고, 현장에 없는 번호는 골라서 재추첨한 뒤 확정한다.
4. 명찰의 번호와 대조해 선물을 준다. 지급 여부는 시스템에 기록하지 않는다.
5. 행사가 끝나면 CSV로 결과를 내려받는다.

## 2. 어떻게 만들기로 했나

주제별로 정리한 결정 사항이다. `D-번호`는 개발 명세서가 참조하는 식별자이므로 바꾸지 않는다. 결정이 바뀌면 여기를 먼저 고치고 개발 명세서의 해당 장에 반영한다. 아직 정해지지 않은 것은 2.4에 모았다.

### 2.1 참가자

| 항목 | 결정 | D |
|---|---|---|
| 참가번호 | 사전 명단은 없다. 마케팅팀이 부여한 1~999 번호를 쓰고 사이트에서 새로 발급하지 않는다. `7`과 `007`은 같은 번호로 보고 정수로 저장한다. 화면과 CSV에는 `7`처럼 앞자리 0 없이 표시한다 | D-02 |
| 번호 변경과 복구 | 별도 버튼 없이 입력란의 번호를 고쳐 [현황 확인하기]나 [방문 인증하기]를 누르면 그 번호로 조회·인증되고 저장 번호도 바뀐다. 다른 기기에서 같은 번호를 입력하면 서버 기록으로 현황이 복원된다 | D-07 |
| 현장 방문 검증 | QR 주소에 추측할 수 없는 토큰을 넣어, 주소를 손으로 쳐서 인증하는 것만 막는다. 위치 확인(GPS) 같은 추가 검증은 하지 않는다 | D-08 |
| 당첨 안내 | 참가자 화면에는 당첨 여부를 표시하지 않는다. 당첨 번호는 발표 화면에만 나온다 | D-05 |
| 본인 확인 | 시스템으로 하지 않는다. 선물을 줄 때 명찰의 번호와 대조한다 | D-06 |

### 2.2 추첨과 선물

| 항목 | 결정 | D |
|---|---|---|
| 경품 구조 | 경품은 등급별로 여러 개이고, 경품마다 당첨 인원이 다르다. 낮은 등급부터 한 경품씩 순서대로 추첨한다 | D-13 |
| 경품 목록 등록 | 경품 목록(이름, 인원, 순서)은 관리자 콘솔에 미리 등록한다. 추첨 화면은 그 순서대로 진행하고 [다음 경품 →]으로 넘어간다. 무대 위에서 인원과 경품명을 입력하지 않는다 | D-19 |
| 회차 간 중복 당첨 | 이전 회차 당첨자는 다음 추첨에서 제외한다. 추첨 화면에 포함 여부 스위치를 둔다 | D-04 |
| 부재자 재추첨 | 추첨 결과는 임시 상태로 먼저 보여 준다. 현장에 없는 번호를 골라 [선택 번호 재추첨]을 누르면 그 자리만 다시 뽑는다. [당첨 확정]을 눌러야 회차가 끝나고, 확정 전에는 다음 경품으로 넘어갈 수 없다. 재추첨된 부재자는 같은 회차에서는 다시 뽑히지 않지만 다음 경품에서는 다시 후보가 된다 | D-18 |
| 결과 보존 | 추첨 결과는 서버에 저장한다. 모달을 닫거나 새로고침하거나 다시 로그인해도 남는다. 발표 화면 옆에 확정된 당첨 번호를 경품별로 누적 표시한다 | D-10 |
| 발표 화면 조작 | 관객이 보는 발표 화면에는 버튼·입력란·안내문을 두지 않는다(마케팅팀 요청, 10/19). 운영자는 키보드로만 조작한다: Space 추첨 시작·고른 번호 재추첨, Enter 당첨 확정, → 다음 경품, Tab 단축키 안내, Esc 닫기(D-22). 연출은 숫자 릴, 당첨 번호는 상자 없이 인원에 따라 크기를 조절한다(개발 명세서 3.4) | D-20 |
| 경품 사진 | (10/22 폐기) 경품 사진을 보여 주지 않기로 했다. 콘솔 경품 목록의 사진 주소 입력과 발표 화면 경품 소개의 사진을 뺀다. DB 의 `image_url` 열은 지우지 않고 둔다. 원래 결정: 경품마다 사진 주소를 적어 발표 화면 경품 소개에 사진·이름·당첨 인원을 보여 준다(참고: splex7/lucky-number-draw) | D-21 |
| 추첨 설정 위치 | 관객에게 보이던 추첨 설정을 발표 화면에서 뺀다(마케팅팀 피드백, 이슈 #4). 관리자 콘솔에는 「이전 당첨자 제외」만 두고, 당첨 인원은 경품 목록 값을 쓰며 추첨 후보 수는 보여 주지 않는다. 값은 DB 가 아니라 브라우저 저장소에 두어 같은 브라우저의 발표 화면과 나눠 쓴다. 발표 화면의 운영자 패널(Tab)은 단축키 안내만 한다. 키는 줄여 재추첨을 Space 로 합치고 일시정지(P)·이전 결과(H)는 없앤다. 추첨 로직은 바꾸지 않는다(개발 명세서 3.3, 3.4) | D-22 |
| 추첨 연출 | 당첨 칸이 인원만큼 처음부터 각자 세 자리 릴로 돌고, 첫 칸부터 하나씩 백→십→일 순으로 멈춘다. 첫 릴 1.5초, 자릿수 간격 0.5초, 한 칸이 멈춘 뒤 MC 가 번호를 발표하는 1초를 두고 다음 칸이 멈춘다. 번호는 003 처럼 세 자리로 채우고 배치는 오름차순 그대로, 멈춘 칸에 띠·상자를 두지 않는다(마케팅팀 피드백, 10/22). 격자 소거·로또 공(직접 계산, 물리 엔진)·동시 릴 목업 4종을 비교해 정했다(개발 명세서 3.4) | D-23 |
| 추첨 대상 지정 | 관리자 콘솔 참가자 목록에서 완주자에게 「추첨 대상」을 체크하고(완주 전에는 체크 불가, [대상 저장] 버튼을 눌러야 저장. 10/23 에 즉시 저장에서 버튼 저장으로 바꿈), 경품 목록에서 「대상자 적용」을 켠 경품은 체크한 완주자를 먼저 뽑는다. 체크한 후보가 당첨 인원 이상이면 그 안에서만 무작위, 적으면 전원을 넣고 나머지는 다른 후보에서 무작위로 채운다. 「이전 당첨자 제외」가 켜져 있으면 체크한 사람도 이전 당첨자면 빠진다. 이미 추첨한 경품의 체크는 잠근다(개발 명세서 A-27, 6장) | D-24 |
| 선물 지급 기록 | 하지 않는다. 선물은 현장에서 명찰의 번호와 대조해 주고(D-06), 지급 여부와 시각을 시스템에 남기지 않는다 | — |
| 필터와 추첨 후보 | (10/15 삭제) 「완주자 중 선물 미지급자」 필터는 지급 기록이 없어져 뺐다. 추첨 후보는 계속 「완주자 − 제외 대상」으로 계산한다 | D-09 |
| 중복 지급 방지 | (10/15 삭제) 지급 기록을 하지 않으므로 필요 없다 | D-11 |
| CSV 열 | 참가번호, 구역별 인증 시각, 완주 여부, 당첨 경품 | D-17 |

| 항목 | 결정 | D |

| 테스트 방침 | 코드는 AI가 작성하므로 TDD로 진행한다. 참가번호 정규화, 완주 판정, 추첨·재추첨, 회차 상태, 세션 토큰, CSV 생성은 Vitest 단위 테스트를 먼저 쓴다. 화면과 API 연결은 수동 확인 | — |

## 4. 비용

| 서비스 | 무료 한도 | 예상 사용량 |
|---|---|---|
| Netlify | 월 300 크레딧. 초과하면 모든 사이트가 멈추고 추가 구매는 불가 | 200 크레딧 이내 |
| Supabase | DB 500MB, 프로젝트 2개 | 10MB 이내 |

Netlify 크레딧 단가는 운영 배포 1회 15, 전송량 1GB당 20, 요청 1만 건당 2, 함수 실행 1GB-시간당 10이다. 미리보기 배포(Deploy Preview)는 크레딧을 쓰지 않는다. 그러므로 개발 중 확인은 미리보기로 하고, 운영 배포는 확정본만 한다.

| Netlify 크레딧이 소진되어 사이트가 멈춘다 | 대시보드에서 남은 크레딧과 결제 주기 시작일을 확인한다. 행사 직전에는 불필요한 운영 배포를 하지 않는다 |
| 관리자 화면을 오래 켜 두어 요청이 쌓인다 | 자동 갱신은 탭이 보이지 않으면 멈추고, 일정 시간이 지나면 자동으로 꺼진다 |
| 행사장 통신이 불안정하다 | 인증에 실패하면 [다시 시도] 버튼을 보여 준다. 참가번호는 브라우저에 저장되어 있어 다시 들어오면 이어서 쓸 수 있다 |
| 카카오톡·네이버 같은 인앱 브라우저나 시크릿 모드에서는 브라우저 저장소가 사라질 수 있다 | 번호를 다시 입력하면 서버 기록으로 현황이 복원된다(D-07). 현장 안내문에 「번호를 다시 입력하면 된다」고 적는다 |
| 다른 사람의 번호를 입력해 대신 완주하거나 당첨을 가로챈다 | 시스템으로 막지 않는다. 선물을 줄 때 명찰의 번호와 대조한다(D-06) |
| 당첨자가 현장에 없다 | 발표 화면에서 그 번호를 골라 재추첨한다(D-18). 확정 전까지는 몇 번이든 다시 뽑을 수 있다 |
| 운영 주소가 바뀌면 QR을 다시 인쇄해야 한다 | D-01 확정 후 주소를 바꾸지 않는다 |
| 리허설 뒤 테스트 데이터를 지우다가 실수한다 | DB가 하나이므로(D-16) 삭제는 정해진 SQL 한 벌로만 한다. 구역과 경품 목록은 남기고 참가자·방문·추첨만 지운다. 지운 뒤 관리자 콘솔에서 참가자 0명, 추첨 0회를 확인한다 |

## 6. 행사 당일 체크리스트

- [ ] 운영 주소에 접속하고 관리자 로그인이 되는지 확인한다.

- [ ] 추첨용 대형 화면과 스피커를 연결한다.
- [ ] 경품 목록이 이름, 인원, 순서대로 등록되어 있는지 확인한다.
